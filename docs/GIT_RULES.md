# Git and Commit Rules

These rules apply during BUILD MODE and to the final public repository.

## 1. Repository bootstrap

The project starts with no Git repository and no remote.

At the beginning of BUILD MODE:

1. If `.git` does not exist, initialize the repository with `git init -b main`.
2. Use `main` as the normal development branch for this small test task.
3. Use the developer's existing Git identity. Never configure a bot/tool identity.
4. If `user.name` or `user.email` is missing, first try to obtain the authenticated developer identity from the available GitHub CLI/account and configure it repository-locally. Ask the developer only if a valid personal identity cannot be determined.
5. Do not create meaningless setup-only commits. The first commit should contain a coherent working bootstrap.

Do not rewrite or squash meaningful history before submission.

## 2. Commit frequency

Commits must be meaningful and reasonably atomic, but not excessively frequent.

- Do not commit per function, method, file, tiny fix, or every endpoint.
- Prefer one commit per coherent build batch or independently useful change.
- The mandatory project will normally produce about 5-8 substantive commits. This is a guideline, not a quota.
- A batch may be split only when it clearly contains two independent concerns.
- Small corrections discovered while verifying the current batch belong in the same commit when they are part of that batch.
- A later bug discovered after a batch was committed should normally be a separate `fix` commit.

The goal is a history that shows real development steps without noise.

## 3. Conventional Commit format

Use English Conventional Commit subjects:

`<type>(<scope>): <Imperative summary>`

The scope is optional. Use it only when it adds useful context.

Allowed common types:

- `feat` — new user-visible or API functionality;
- `fix` — bug or incorrect behavior fix;
- `docs` — documentation-only changes;
- `refactor` — code restructuring without a feature or bug fix;
- `test` — tests only;
- `chore` — build/config/dependency/routine maintenance;
- `style` — formatting-only changes with no behavior change.

Examples:

- `chore: Bootstrap Symfony application`
- `feat(domain): Add task and status entities`
- `feat(status): Implement status API`
- `feat(task): Implement task API`
- `fix(api): Harden validation and errors`
- `docs: Complete setup and architecture guide`
- `test(api): Cover critical task flows`

Avoid vague subjects such as `update`, `changes`, `fix stuff`, `final`, `work`, or `misc`.

## 4. Subject rules

Combine Conventional Commits with the commit-message rules from the provided guidance:

- Keep the Conventional Commit type/scope lowercase.
- Start the summary after `: ` with a capitalized imperative verb when natural: `Add`, `Fix`, `Update`, `Remove`, `Refactor`, `Document`.
- Use imperative mood: the subject should complete “If applied, this commit will ...”.
- Do not put a period at the end of the subject.
- Aim for a full subject line of about 50 characters or less when practical.
- Never exceed 72 characters without a strong reason; rewrite instead.
- Describe one coherent change.

## 5. Commit body

A body is optional. Do not add one when the subject is sufficient.

When a body is useful:

- separate it from the subject with one blank line;
- explain **what** changed and **why** it was needed, not a line-by-line description of **how** the code works;
- mention non-obvious trade-offs or side effects;
- wrap prose at roughly 72 characters where practical;
- keep it concise.

Do not add decorative templates or empty sections.

## 6. No tool/AI attribution in Git metadata

Branch names, commit subjects, commit bodies, tags and repository names must not mention development tools or AI providers.

In particular, do not include terms such as:

- `Codex`
- `OpenAI`
- `ChatGPT`
- `AI-generated`
- `generated by AI`
- `agent`

Do not add AI/bot attribution trailers such as `Co-authored-by`, `Generated-by`, or similar metadata referring to a tool/assistant.

Commits must use the developer's Git author identity, not a bot identity.

This rule concerns Git/repository metadata. The final README must still satisfy the assignment's explicit requirement to describe AI-assistant usage honestly; that section should be factual and concise and does not need to name a vendor unless the developer wants to.

## 7. Branch policy

For this small take-home project, work directly on `main` during initial development unless a separate branch is genuinely needed.

If a branch is needed, use neutral purpose-based names such as:

- `feat/task-api`
- `fix/status-delete-conflict`
- `docs/readme`

Never include tool/provider names in branch names.

After the submission commit/hash has been sent to the recruiter, do not push additional changes to `main`. Any later fixes must go to a separate purpose-based branch.

## 8. Autonomous commit workflow

The development agent owns routine Git operations during BUILD MODE.

After a coherent batch:

1. run relevant verification;
2. inspect `git status` and `git diff`;
3. ensure no secrets, temporary files, database files, IDE artifacts, or unrelated changes are staged;
4. stage only the coherent batch;
5. create the commit automatically using these rules;
6. record the resulting commit hash/message in `docs/STATE.md`;
7. continue to the next batch without waiting for developer approval.

Stop and ask only when there is a real blocker, destructive ambiguity, secret exposure, or missing authentication/identity that cannot be resolved safely.

## 9. Public GitHub repository

Development begins locally. Do not require the developer to create a repository first.

Once the mandatory build is complete and the fresh-run verification passes:

1. verify the local history is clean and meaningful;
2. ensure the default branch is `main`;
3. attempt to create a **public GitHub repository** using the developer's already authenticated GitHub account;
4. prefer the neutral repository name `skyeng-task-manager`;
5. if that name is unavailable, try `skyeng-backend-task-manager`;
6. add it as `origin` and push `main` with the complete existing history;
7. verify the remote and report the resulting repository URL.

Prefer `gh repo create ... --public --source=. --remote=origin --push` when GitHub CLI is available and authenticated.

If repository creation or push cannot be completed because authentication/tooling is unavailable, do not invent a remote or credentials. Ask the developer only for the minimum action needed to unblock GitHub access.

## Reference principles used

The commit-message style combines the supplied Conventional Commits examples with these practical principles:

- separate subject and body with a blank line;
- concise subject, ideally around 50 characters;
- no period at the end of the subject;
- imperative subject;
- body around 72 characters per line when present;
- body explains what and why rather than narrating implementation details.
